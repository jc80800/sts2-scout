# Development-only AI-assisted seeding

The current bundled catalog and repeatable API refresh are documented in [catalog research](catalog-research.md). This original workflow remains for additional hash-bound, manually reviewed strategy claims.

`tools/Scout.Seeder` is not referenced by or packaged with the desktop application. It accepts **saved** webpages/API responses and user-authored files through `SourceManifest`; no URL is fetched automatically. APIs/URLs are exact provenance allowlist entries, each mapped to a saved file. No source is preapproved, including Spire Codex. A human must check current access conditions, license, retention and redistribution rights before downloading/ingesting external material. Merely being public does not confer redistribution rights.

## Workflow

1. Create a catalog JSON matching `schemas/strategy-pack.schema.json`, using original normalized facts and IDs whose use is permitted. Set a precise game version, unique pack version, and empty claims. Entity fields: `id`, `name`, `kind` (Card/Relic/Potion/Service), heuristic `baseline`, `tags`, `setupRisk` (0–10). Do not use synthetic test IDs for real game play. No winning-deck correlation is a causal win-rate estimate.
2. Create `sources.json` matching `schemas/sources.schema.json`. Each entry records the exact source URL, savedPath (relative to the manifest or absolute), retrieval/publication dates, game version, license/terms decision, terms-check timestamp, allowIngestion and allowRawRetention. An explicit URL absent from this list is rejected. Sources requiring deletion/no retention cannot enter this implementation because reprocessing evidence must remain available.
3. Run `prepare` to produce a model prompt from one approved saved source. Provide the catalog and candidate schema to your chosen development-time model alongside the prompt. Treat source text and model output as untrusted. Running this command does not send data to any model. Before submitting material to an external model yourself, ensure your source permissions permit it. Save its JSON array response locally. The `IAiExtractor` interface permits a future development-only provider; the shipped implementation imports saved responses without an API key.
4. Run `ingest`. It validates strict JSON shape/enums, IDs, dates, bounds, patch applicability and provenance; all duplicate IDs or duplicate semantic claim bodies are quarantined. Invalid JSON fails the entire import before promotion. Missing source licenses or retention permissions are rejected. Valid claims enter candidate state, never approved state.
5. Review `candidates.json`, including `quarantine` and `conflicts`. Opposing signed weights for the same relationship remain separate claims; no source silently wins. Inspect the evidence at each evidenceLocator. The evidence directory contains original approved source bytes, named by SHA-256, so extractors can reprocess them without refetching. It is private development data and is excluded from the runtime artifact.
6. Edit `review.json`: for every candidate set decision to `approved` or `rejected`, enter your reviewer name, and an ISO 8601 reviewedAt timestamp. Keep the generated claimHash. If you edit a candidate, re-ingest and review the new hash. Conflict participants require individual decisions; approving both keeps both and the engine explains both contributions.
7. Run `compile` with a new pack version. It requires exact-content review and retained evidence hashes, revalidates claims, and refuses to overwrite an existing output. The compiled pack contains normalized reviewed claims and provenance, not raw source text/images. Check redistribution rights for derived claims separately before distributing. Local compilation is not publication approval.
8. Quit Scout and install the pack as `%LOCALAPPDATA%\Sts2Scout\strategy-pack.json`; keep game version aligned with settings and calibration. Raw evidence and seeding tools stay out of the application folder.

```powershell
dotnet run --project tools/Scout.Seeder -- prepare .\sources.json https://YOUR-APPROVED-URL .\prompt.txt
dotnet run --project tools/Scout.Seeder -- ingest .\catalog.json .\sources.json .\ai-response.json .\seed-output
# Review candidates.json and edit seed-output/review.json before the next command.
dotnet run --project tools/Scout.Seeder -- compile .\catalog.json .\seed-output .\seed-output\review.json local-1 .\strategy-pack.json
```

For a fully legal deterministic rehearsal, replace the first three ingest paths with `tests/Scout.Tests/Fixtures/catalog.json`, `tests/Scout.Tests/Fixtures/sources.json`, and `tests/Scout.Tests/Fixtures/ai-response.json`. This creates two intentionally conflicting synthetic claims. The tests mock AI by importing that saved response and prove invalid/duplicate/unprovenanced claims cannot be promoted.

Supported claim kinds: CardSynergy, RelicSynergy, AntiSynergy, Archetype, DeckNeed, MerchantPriority. Synergies/anti-synergies require an `other` entity; archetypes/needs require a tag. Weights are signed, bounded heuristic contributions; anti-synergies should use negative weights. Source confidence scales the contribution. Claims are directed (`subject` receives the contribution); add a separately reviewed reverse relationship if warranted. Exact patch matching is intentionally conservative; future patch-range support must define its own compatibility rules.
